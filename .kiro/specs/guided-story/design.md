# Guided Story Design

## Architecture

Server-rendered pages (FastAPI, Jinja2) enhanced with htmx. Business logic lives in one new module, `coroner/ui/story.py` (quality.md: no business logic in routes or templates); routes only call it and render. Templates hold sentences and layout, never measured values.

```
GET /story, /story/step/{n}?view=      full page, or fragment when HX-Request is present
POST /story/gate-check                 fragment, calls gate_check() (the /api/gate-check route function)
POST /story/run                        fragment, calls run_audit() (the /api/run route function)
GET  /story/job/{job_id}               fragment, calls job_status(), polled every 2 s
POST /story/tamper                     fragment, calls tamper_certificate() (the /api/tamper route function)
GET  /fool?case1=on&case2=on&case4=on  full page or fragment
static/story.js                        arrow and Escape shortcuts only
```

Everything the pages show comes from `story.py` functions that read files (Req 3). The routes under /story that start work (gate check, run, tamper) call the existing route functions, so the limits of D-54 (global 100 per minute, 20 per minute per client, /api/run 5 per minute and one active audit per client, gate-check and tamper 1 per 10 seconds per client on a cache miss, 16 KB body, no-store) apply unchanged. The `/story/*` HTML routes get `Cache-Control: no-store` and `Vary: HX-Request`.

## Data sources (what init_demo_runs.sh generates)

scripts/init_demo_runs.sh, run by the coroner-init service at first start (CORONER_BASE_DIR=/data), produces:

| Command in the script | Run directories |
|---|---|
| `coroner verify` T1 faulty, 2000 cases, seed 42 (expects exit 1) | T1 ZOMBIE run |
| `coroner verify` T1 correct (expects exit 0) | T1 ALIVE run |
| `coroner verify` credit-fees correct (exit 0) and `build/variants/CreditFees.java` HALF_EVEN (exit 1) | credit-fees runs (not used by the story) |
| `python -m coroner traps` | for T1 to T5, one faulty and one correct run at 2000 cases, seed 42, plus `runs/trap_catalog.json` and `.txt` |

Decision: the story and the fool page use these bundled runs and start no audit of their own. Reasons: the T2 and T4 verdicts needed by the toggles are already generated by `coroner traps`; an on-demand audit per toggle would cost 3 audits against the one-audit-at-a-time queue and make a toggle slow; and the verdict shown is then the same run id the Detection Matrix lists. The run ids are read from `runs/trap_catalog.json` (`faulty_run_id`, `correct_run_id` per trap id), because the catalog is the only file that lists T2 and T4 ids. "Run it yourself" in steps 4 and 7 is the only place where an audit starts, through the existing job API.

Local `runs/trap_catalog.json` today (read 2026-11-21, for orientation only; the code reads it at request time): T1 faulty f584d5f35228 and correct 29c15f04407b; T2 faulty 26b427d5d678 and correct aa44200e06b4; T4 faulty e00ac9d50c76 and correct 1c1b8639eb0c.

Files read per run: `verdict.json` (keys `status`, `sub_label`, `cases_total`, `cases_divergent`, `exposure_sum`, `exposure_max`, `affected_branches`, `suspense_difference`, `grand_total_matches`), `branch_reconciliation.json` (`branches[]` with `branch`, `cobol_subtotal`, `java_subtotal`, `difference`, `absolute_difference`, `status`; `suspense` with `cobol`, `java`, `difference`; `grand_total` with `cobol`, `java`), `failure_report.json` (`case_id`, `divergent_fields[]` with `kind`, `output_key`, `cobol_values`, `java_values`), `card.txt` (Given, Then and "COBOL lines involved"), `comparison_results.json` (`cases[]` with `divergent`, `divergent_fields`), `inputs.json`, `certificate.json` (`status`, `case_count`, `cases_divergent`, `random_seed`, `certificate_sha256`, `cobol_file`, `java_file`), `timing.json`, `generated_cases.csv`.

Note (observed in a real run): `failure_report.json` `input_row` is the first row of the original multi-row case, not the minimal subset (for the T1 run it shows branch D04, while the minimal case is one transaction on branch 001). The example on step 5 therefore uses `card.txt` and `minimal_case_input.csv`, never `input_row`.

Note: docs/video-plan.md names the exposure keys `unreconciled_exposure.sum` and `unreconciled_exposure.branches_affected`; the real `verdict.json` keys are `exposure_sum` and `affected_branches`. The story uses the real keys. The video plan is outside this spec; the first task reports the mismatch to the owner of that file.

## story.py (data layer)

Functions, each pure over files and unit-tested:
- `load_cases_registry()` reads samples/traps/cases.json.
- `load_catalog(base_dir)` reads runs/trap_catalog.json and returns, per trap id, `faulty_run_id`, `correct_run_id` and the entry; raises a typed error when the file or a run is missing (the routes turn it into the "Bundled demo runs missing" alert).
- `load_run(base_dir, run_id)` returns a small object with the parsed files above (each optional file is `None` when absent; no defaults).
- `listing(trap_dir, cobol_path, anchor_ids, executed_lines)` resolves each anchor of trap.json `listing` against the COBOL file: line numbers, text, executed flag.
- `first_divergent_case(run)` returns the first case of `comparison_results.json` with `divergent` true, its 1-based position and `cases_total`.
- `exhibits(run, run_dir)` returns the evidence files that exist, in the fixed order certificate, failure report, minimal case, JUnit test.
- `transaction_count(run)` counts data rows of `generated_cases.csv`.
- `fool_state(base_dir, selected)` returns, per toggle, the shown run, verdict, counts, plus N, D, C and M (Req 15).
- `t2_column_counts(run)` counts divergent FEE1 and FEE2 values from `comparison_results.json`.
- `normalize_view(value)` returns `business` or `engineer`.

The story reuses `generate_zombie_sentence` (coroner/ui/sentences.py), the existing branch table sorting and bar widths computed for the run page, and the existing verdict badge macro. Where a function is needed by both the run page and the story, it is moved to `story.py` or `pages.py` and the run page imports it (no duplicated logic, no change of the run page output; its existing tests stay green).

## Case registry

`samples/traps/cases.json`:
```json
{"T1": {"case": 1, "name": "The Missing Branch"}, "T2": {"case": 2, "name": "The Vanishing Cent"},
 "T3": {"case": 3, "name": "The Negative That Wasn't"}, "T4": {"case": 4, "name": "The Sign of Zero"},
 "T5": {"case": 5, "name": "The Silent Zero"}, "T6": {"case": 6, "name": "reserved"}}
```
One file also covers T6, which has no trap.json. `coroner/traps.py` adds `case_number` and `case_name` to each catalog entry (T6 included) from this registry; the Matrix page, the home page selector and the run page header read the names from the registry or from the catalog entry. Display form: "Case N Name".

## Steps

Each step is one template block with: the step heading (focus target), one plain sentence (typed prose, no measured value inside it), the measured content, the listing panel when anchors exist, and Back and Next links. The Engineer view adds a "Technical details" block. Sentences below are the typed prose; every `{...}` is a value read from the named file.

1. Bank process. Prose: "Every night, the bank reconciles branch subtotals to catch posting errors before opening." Listing: `table`. Engineer: the schema file name and its input columns (`schema.json`), the COBOL file name and the `table` line range.
2. COBOL result. Prose: "The COBOL program posted {transactions} transactions in {cases} test batches." Content: table of branch, COBOL subtotal (`branch_reconciliation.json`, `cobol_subtotal`, suspense `cobol` as its own row) and the COBOL grand total. Source run: the T1 faulty run (the COBOL column is the same in the correct run because both use the same generated cases; the story uses one run so the figures agree across steps). Listing: `collation`, `sort`. No verdict badge here (an ALIVE badge on the COBOL result confused the earlier draft; ALIVE and ZOMBIE are verdicts of the comparison).
3. Java migration. Prose: "A Java version was written to replace it." Content: "COBOL grand total {c}, Java grand total {j}", followed by "They match." only when the two strings are equal, else "They differ." (decided by comparing the values, not by `grand_total_matches` alone). No verdict and no branch table yet, so step 4 shows the finding. Engineer: Java file name from `certificate.json` `java_file`.
4. Coroner compares. Prose: "Coroner ran both programs on the same {cases} test batches." Content: verdict badge, `generate_zombie_sentence` text (Business), "{cases_divergent} of {cases_total} batches diverge", three figures (exposure sum, affected branches, grand total balances) from `verdict.json`, the gate fragment, "Run it yourself". Engineer: run id, seed, duration, exposure maximum, suspense difference, return codes.
5. Where and why. Prose: "Coroner found where the migration broke and why." Content: the branch table limited to MISMATCH branches ("N other branches match" from the same file), "Posted to suspense instead of a branch: {suspense difference}", then the autopsy blocks of Req 14: Cause of death, Time of death, Exhibits. The example is the Given and Then lines of `card.txt`. Listing: `match`, with the executed lines of the card marked. Engineer view of Cause of death lists `kind`, `output_key`, field names and the `cobol_rule` with its anchor lines.
6. Apply the fix. Prose: "The corrected Java version orders branch codes the way the COBOL program does." Content: `business_fix` (Business) and `fix_sentence` (Engineer) from trap.json. Listing: `match`.
7. ALIVE certificate. Prose: "Coroner audited the corrected version on the same test batches." Content: verdict badge, "{cases_divergent} of {cases_total} batches diverge", exposure sum, the gate fragment, "Run it yourself" (correct port), Exhibits (certificate only). Engineer: run id, `certificate_sha256` prefix, seed. The certificate is shown as valid only after the replay (gate result "Commit allowed").
8. Try to cheat. Prose: "Try to make the rejected migration look clean by editing its certificate." Content: the Tamper form for the T1 faulty run, prefilled from its `certificate.json` (status, divergent count, seed, and the case count under the key the endpoint really edits); an instruction line "Change the status to ALIVE and the divergent count to 0" (typed instruction, not a measured value); the result fragment; the closing sentence "Editing a certificate makes it INVALID. The audit result cannot be faked." The story uses the faulty run because editing the certificate of an ALIVE run to ZOMBIE would not cheat anything.

## Gate fragment (steps 4 and 7)

A form `hx-post="/story/gate-check"` with hidden `run_id` and `view`, button "Check the gate", target `<div role="status" aria-live="polite">`. While the replay runs, htmx shows `hx-indicator` text "Checking the gate. This replays the audit." (no duration claim). The route calls `gate_check(request, run_id)` and renders the returned JSON:
- 200 blocked: red square, message from the response ("This ZOMBIE migration cannot be committed"), "Exit code {exit_code}".
- 200 allowed: green circle, "Commit allowed", "Exit code 0".
- 200 blocked with the invalid-certificate message: amber triangle, the message as returned.
- 429: `role="alert"`, endpoint detail, "Try again in {retry_after} seconds", button "Check again".
- 503: `role="alert"`, "Replay did not complete, try again", button.
- 404 or 413 or 500: `role="alert"`, the detail.

## Run it yourself (steps 4 and 7)

A small form (seed, cases, `view`) posts to `/story/run`, which calls `run_audit(request, sample="T1", port=<fixed by step>, seed, cases)`. 202: the fragment contains `<div hx-get="/story/job/{job_id}" hx-trigger="every 2s" hx-swap="outerHTML" role="status" aria-live="polite">` showing "Audit running". `/story/job/{job_id}` calls `job_status(job_id)`: queued or running returns the same polling div; done returns the verdict badge, "{cases_divergent} of {cases_total} batches diverge" read from that run's `verdict.json`, and a link to the run page, and no `hx-trigger` (polling stops); error returns the reason in a `role="alert"` region. 200 cached: "This exact audit already exists", with the stored run's numbers. 422, 429: alert with the detail. The visitor's run never changes the numbers of the other steps; the page labels it "Your run".

## Tamper (step 8)

Form `hx-post="/story/tamper"` with fields `run_id`, `status`, `cases_total` (or the real key, see Req 4), `cases_divergent`, `random_seed`, `view`. The route calls `tamper_certificate(...)` and puts its HTML result in `<div role="status" aria-live="polite">`; a 429 or 422 becomes a `role="alert"` message. The original certificate file is never modified (existing behavior, asserted by hash in the test).

## Fool page

`GET /fool?case1=on&case2=on&case4=on&view=`. `fool_state` returns three toggle rows. Markup: `<form method="get" action="/fool">` with a `<fieldset><legend>Inject a defect</legend>`, three labelled checkboxes, an "Update" button (hidden by CSS only when htmx is active through `hx-trigger="change"`; shown in `<noscript>`), and a result region `<div id="fool-result" role="status" aria-live="polite">`. Each row shows: the case name, the defect description, the shape-and-text verdict of the shown run, "{cases_divergent} of {cases_total} batches diverge" for a faulty run, the ZOMBIE sentence from `generate_zombie_sentence`, and a link to the run page. Below, the counter (Req 15). One sentence states that the ports are fixed repository files audited ahead of time with the case count and seed read from `inputs.json`, and that no code is uploaded.

The defect captions (typed prose, not measured): Case 1 "Branch codes compared in ASCII order instead of EBCDIC order"; Case 2 see Uncertain; Case 4 "The zero overpunch characters { and } are not decoded". For Case 4 the Engineer view also shows, computed from the run's `comparison_results.json`, how many divergent values come from "}" in the input; nothing is claimed about "{" without that count (the measured fact of R-87 is that only "}" diverges).

## Listing panel

trap.json for Case 1 gains `listing` (anchors `collation`, `table`, `sort`, `match`) and `cobol_rule`. `listing()` reads the COBOL file named by the run's `inputs.json` `cobol_file`, resolved under the repository's samples/traps folder (the same resolution the run page uses for trap.json); no user-controlled path exists. Output markup: `<details>` (closed in Business view, open in Engineer view) containing `<div role="region" tabindex="0" aria-label="MATCH-MERGE.cob lines 201 to 223" style="overflow-x:auto"><pre>` with one line per source line: line number, text (HTML-escaped), and the word "executed" in a visually distinct tag for marked lines. The extractor returns an explicit error object when a pattern matches nothing.

## Keyboard and focus

static/story.js (about 20 lines, loaded with `defer`): on `keydown`, ignore events with modifiers or when `document.activeElement` is an input, select, textarea or button; ArrowRight follows the Next link, ArrowLeft the Back link, Escape navigates to "/". After `htmx:afterSwap` on `#story-content`, it focuses the step heading. Without the script, links and the native Enter and Tab behavior remain.

## No-JavaScript behavior

Pages render fully on the server. Next, Back, Business view, Engineer view and the fool toggles are links or a GET form. The three action forms (gate, run, Tamper) carry a `<noscript>` note with the equivalent: open the run page and use its Verify or Tamper link, or run `python3 -m coroner verify <certificate.json>`. (The run page's own Verify and Tamper also need htmx today; the note names the CLI command as the equivalent that always works.)

## Responsive design

At 375 px: single column, full-width buttons of at least 44 px, body text 16 px or more, tables and the listing panel scroll inside their container, no horizontal page scroll. CSS lives in base.html's existing variables; new rules use the same variables so dark and light modes and the contrast tests cover them.

## Tests

- `tests/test_story_registry.py` (fast): registry has exactly the six entries; README trap table names equal the registry; Matrix page, home selector and run page header show "Case N Name"; T6 shows "Case 6 reserved" and no numbers; the catalog entries gain `case_number` and `case_name`.
- `tests/test_story_listing.py` (fast): the extractor, run on the real MATCH-MERGE.cob, returns the line numbers a test computes independently by scanning the file; a changed copy of the file moves the numbers; an unmatched pattern gives the explicit error; the text equals the file's lines; HTML escaping.
- `tests/test_story_pages.py` (slow, session fixture `story_runs` that runs the real catalog in a temporary base): one test per step, each reading its expected values from the run files with the helper; Business and Engineer views per step (a Business page contains none of the Engineer labels; the Engineer page contains each listed detail from the file); step 5 autopsy (cause, first divergent case equals an independent scan of `comparison_results.json`, exhibits equal the files present); gate fragment blocked and allowed through the real route; 429 and 503 fragments (rate window set by CORONER_GATE_CHECK_RATE_WINDOW, replay timeout forced with CORONER_REPLAY_TIMEOUT=1); run-it-yourself with 20 cases and the cached case; Tamper result INVALID and original certificate hash unchanged.
- `tests/test_story_fool.py` (slow, same fixture): each toggle on and off; counter values equal counts recomputed from the verdict files; a run whose verdict is edited in the temporary copy to ALIVE lowers D and not N (proves the counter is computed); a missing run disables its toggle and leaves N; T2 column counts equal an independent scan.
- `tests/test_story_a11y.py` (fast, plus slow where a run is needed): positioning sentence present in the full page; Next and Back are `<a href>`; step heading has `tabindex="-1"`; every async target has `role="status"` and `aria-live="polite"` or `role="alert"`; the listing region has `tabindex="0"` and `aria-label`; the shortcut script contains the guard conditions (modifier keys, input, select, textarea, button) and the Escape and arrow handlers, checked as text; contrast of the new colors with the functions of tests/test_ui_pages.py in both modes; the stylesheet contains the 375 px rules (minimum font size and 44 px targets), checked as text. Behavior at 375 px (no horizontal page scroll, tap targets) and the keyboard shortcuts are checked by a Playwright script run by the operator on the host with the installed Chrome (`SCREENSHOT_CHANNEL=chrome`, as `make screenshots` does); the Playwright extra is not in the Docker image, so this check is not part of CI and its result is recorded in the review entry.
- `tests/test_story_nojs.py` (slow): with no HX-Request header every step page contains its measured values, the listing, the case name and the view links; the fool GET form with parameters shows the right counter.
- Constraint tests: no em dash in the new templates, static file, story.py, cases.json and trap.json; `git status` of the repository root shows no new file after the suite (the existing root-file guard also applies).

## Rate limits and security

- Run ids: 12 lowercase hex, validated by the existing functions; job ids by `validate_job_id`.
- All values inserted into HTML are escaped (Jinja autoescape; fragments built in Python use `html.escape`).
- No new file path comes from the request. The listing reads only the COBOL file of a validated run, resolved under samples/traps.
- Fragment routes add no limiter of their own and bypass none (Req 4).
- SECURITY.md and docs/judge-guide.md need a line each for these routes; they belong to the docs track, so this spec only lists the text to hand over (last task).

## Error handling

- Missing catalog or run: the "Bundled demo runs missing" alert, status 200 for the page (the visitor can read the explanation), no numbers.
- Unknown `view`: business. Unknown step: redirect to step 1.
- Gate, run and Tamper failures: alert fragments (see above), never a stack trace.

## Dependencies

None new. FastAPI, Jinja2 and htmx 2.0.4 (vendored). Playwright stays in the `screenshots` extra and is used only by the operator's host check.
